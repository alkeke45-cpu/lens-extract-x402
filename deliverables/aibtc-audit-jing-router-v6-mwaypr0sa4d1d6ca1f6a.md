# Audit — Jing stx-usdcx Router v6 vs v5-5 (AIBTC mwaypr0sa4d1d6ca1f6a)

Scope files: `v6.clar` (1478 lines), `v55.clar` (1123 lines). All line refs are v6 unless marked v55.

## 1. Method & reproducible checks

- `wc -l v55.clar v6.clar` → 1123 / 1478.
- `diff v55.clar v6.clar` → 361 added lines, 6 removed lines, 20 hunks. The 6 removed lines are exactly the two u3004 sum lines and the two smart-swap stage-chaining lines, each replaced by a version adding Zest. Everything else is pure addition: header (1–60), `VENUE_ZEST`/Zest constants (80–84), `leg-zest` (251–288), `zest` fields in both split functions, the Zest smart-swap block (1100–1314), stage chaining (1352–1354, 1423–1425). No v5-5 logic was altered.
- `grep -n "twap|get-mid|trait|as-contract|stx-transfer"` → no `get-mid-twap-swap`, no traits, no `sbtc`, no `zest-ticks-trait`, no `zest-amm-pool-v2-01-20` anywhere in either file; `as-contract`/`stx-transfer?` occur only in the header comment (49–57).
- Python replication of `zest-log2`/`zest-tick`/`zest-ticks`/`zest-bound` (constants copied verbatim): `ZEST_LOG2_WAD` = log2(1e18)·2^60 exactly (tick 0 ⇔ WAD price 1.0, consistent with `ZEST_WAD_PRICE` 1e26 = 1e18·PRICE_SCALE at 1102); `ZEST_LOG2_STEP` within 14 units of log2(1.01)·2^60; `ZEST_FRAC_BITS` = 2^59…2^44 (16 entries). Tick output matched true floor(log₁.₀₁(wad/1e18)) on 16/17 samples; the one miss is wad=1e18 exactly → −1 vs 0 (truncation in the 16-step refinement), absorbed by the ±2 tick margin and irrelevant to price enforcement (see §3). Walk simulations: wide limit truncates to exactly 32 consecutive ticks from the mid side; limit past market → empty walk; endpoints inclusive at bound-tick +1 / −1 as the header states. `zest-bound` matched exact rational floor (x→y) / ceil (y→x) on all samples; largest intermediate 1e34 ≪ 2^128.

## 2. Findings

**F1 — Informational (direct answer to the poster's question): `mid` is not verified on-chain.**
`smart-swap-stx-for-usdcx` (1335) and `smart-swap-usdcx-for-stx` (1406) take `mid` as a plain caller-supplied `uint`. No function named `get-mid-twap-swap` exists in the contract and nothing fetches a TWAP or compares `mid` to any pool/oracle price. Its only uses are Jing capacity quoting (`jing-size`, 620/624) and Zest tick-window selection (`zest-stage`, 1295: `mid-wad = ZEST_WAD_PRICE / mid`). The header itself concedes this (10–11: "mid (untrusted, it only picks which bins are read)"). Impact is bounded: a wrong `mid` can mis-size the Jing leg or make the Zest walk empty/off-market (no fill), but execution prices are enforced independently — Jing/Zest receive limit-derived price arguments and the final balance-measured min-out (u3002, 1357/1428) must pass. It cannot force a fill worse than `limit-price` or below `min-out`, assuming Jing/Zest honour their price arguments (their code is out of scope). Fix (optional, documentation-level): drop any "mid is the quote it returns" wording; state that `mid` is untrusted caller input whose only safety role is none — price safety comes from `limit-price` + u3002.

**F2 — Low (inherited, byte-identical in v5-5): non-zero `xyk`/`velar` allocations always brick split swaps.**
`amm-sell-stx`/`amm-sell-usdcx` (194–214) return `ERR_BAD_VENUE` (u3003) for every venue except DLMM, and `leg-stx`/`leg-usdcx` propagate it via `try!` in both split functions (401–408, 515–522). Yet the u3004 sum check (373–379, 487–493) treats `xyk` and `velar` as legitimate allocations and both fields remain in the public signatures (353–364, 467–478). Scenario: a front-end allocates even u1 to `xyk` → Jing, Zest and DLMM legs execute, then the xyk leg errors and the whole transaction reverts (atomic, so loss is the tx fee only; no funds at risk). Fix: assert `xyk == u0` and `velar == u0` up front with a dedicated error until those venues exist, or exclude them from the u3004 sum.

No Critical, High or Medium findings. No other valid findings in the changed surface.

## 3. Checked and clean

- **Native STX leg, principal in/out:** the router never uses `as-contract`, never calls `stx-transfer?`, and holds no custody (grep above); `tx-sender` is bound once per public function (382, 496, 1343, 1414) and all balance measurements are on `tx-sender`. STX-out is measured as `stx-get-balance` gain (497/523, smart 1415ff.), USDCx-out as USDCx balance gain (383/409); `gain` (102–110) floors at 0. The actual STX pull/payout mechanics inside Zest's `clmm-pool-v1`/`wstx` (header 49–57) are external contracts, not in the provided files — that part is taken as documented, not verified.
- **Partial fills:** split path — `leg-zest` passes `allow-partial-fill=false` (264, 274) and propagates errors via `(err e)` + `try!` (396, 510): all-or-nothing, any Zest failure reverts the whole split tx. Smart path — `zest-swap` passes `true` with min u0 (1256–1258, 1267–1269) and converts any error to `ZEST_NONE` (in=out=0); chaining subtracts actual `(get in zest)` before DLMM/cp (1352–1354, 1423–1425), so a partial Zest fill flows correctly to later stages. Receipt `unsold` in split functions omits a Zest term, which is sound only because the split Zest leg cannot partially fill (above).
- **Tick loop bounds:** hard cap 32 enforced three ways — `(list 32 int)` types (255, 366, 1199), the 32-element `ZEST_WALK` fold (1116–1119), and `as-max-len? … u32` in `zest-tick-step` (1201). Steps are strictly ±1 (monotonic ascending for x→y, descending for y→x, matching the router's stated ordering); start = tick(mid) ∓ 2, end = tick(bound) ± 1 inclusive (1210–1234). Clamp ±4458 (1107, 1167–1185): reachable ticks from `zest-stage` span only [−4166, 1851], so the clamp is dead code in practice; generated ticks could exceed the clamp by ≤2 (margin/end offset) only in unreachable states. Division-by-zero is impossible: `limit > u0` (u3006) and `mid > u0` (u3007) asserted at 1340–1341/1411–1412, fee ≥ 100% forces bound u0 and skips the stage (1297–1300), and ticks are built only when `bound > u0` and `mid-wad > u0` (1300).
- **Mid verification:** see F1 — named nowhere, verified nowhere; safety rests on limit-derived bounds + u3002, which were verified as above.
- **Slippage math, u3004 sum vs per-leg:** both split functions assert exact equality `jing + dlmm + xyk + velar + zest == amount` before any call (373–379, 487–493). `scale-min` (329–338) rescales the DLMM per-leg min pro-rata when a Jing residual is fallback-routed into it; `valid-fallback` (340–345) admits DLMM only, so Zest never receives residuals (matches header). Caveat verified, not a bug: the per-leg Zest min is `amm-floor(amm-mins.zest)` (216–221, 263/273), i.e. floored to u1 when the caller sets it to 0 — per-leg protection can therefore be nominal, and in the smart path the Zest leg's own min is u0 by design (1257, 1268). In both paths the binding protections are the price argument (FE-supplied in split, limit-derived in smart) and the combined balance-measured u3002 check.
- **Trait references / principals:** there are no trait-typed or principal arguments in any public function (signatures at 347, 461, 1331, 1402 — uint/buff/optional/tuple/list only), so there is no trait-substitution surface. All counterparties are compile-time constants. The two distinct wstx contracts are not mixed up: Bitflow `WSTX` (62) is used by Jing (118) and DLMM (167–187) only; Zest `ZEST_WSTX` (83) is used by `leg-zest`/`zest-swap` only (262, 272, 1256, 1267); `USDCX` (63) is used consistently; `ZEST_POOL_ID` u1 (84) and `ZEST_POOL` (1100) match the header's pool (line 4). The bounty-named `sbtc` and `zest-amm-pool-v2-01-20` do not appear in either file.
- **Post-conditions:** Clarity source cannot set post-conditions; none appear in the file. The header's PC description (58–60) is a client-side expectation. The in-contract substitutes were verified: u3002 min-out on balance-measured gain, u3004 split equality, per-leg mins. Balance-delta measurement is sound for a single contract call (only this call's venue calls move the user's balances mid-transaction).
- **Inherited surface:** apart from the 6 replaced lines, all v5-5 code (Jing sizing, DLMM pick/capacity/stage, `cp-stage` stub returning `unsold = left`, fallback logic) is byte-identical, so no regression was introduced. Noted but not counted as a finding: `dlmm-stage` propagates DLMM errors via `try!` while Jing/Zest errors degrade gracefully — pre-existing atomicity trade-off, unchanged by v6.
